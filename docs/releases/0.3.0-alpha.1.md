# Commeatus v0.3.0-alpha.1

This is the third public alpha of Commeatus.

The release turns the policy engine's route result into a real named proxy-outbound execution path. The core still does not know proxy protocol configuration: it chooses an opaque endpoint identity, and the execution registry owns the protocol, address and capabilities behind that identity.

## Included binaries

- Linux x86_64
- Android arm64 (`aarch64-linux-android`, NDK/API 29 baseline)

## Major changes

### Opaque native proxy endpoints

The core now models:

```text
ExecutionPlan
  └─ Route
      ├─ Direct
      └─ Proxy(EndpointId)
```

`EndpointId` is a validated native identifier. It deliberately cannot contain a URI such as `socks5://...`; protocol configuration remains outside the core.

### Outbound execution registry

The daemon now owns an `OutboundRegistry` that maps endpoint identities to execution implementations and capabilities.

The first native proxy outbounds are:

- SOCKS5 no-auth upstream TCP CONNECT
- HTTP/1.x upstream CONNECT

Both implement bounded upstream connect/handshake behavior and preserve a domain target to the upstream proxy instead of resolving that destination locally.

### Native configuration

Example:

```text
endpoint edge-socks socks5 127.0.0.1:1081
endpoint office-http http 127.0.0.1:8081

rule proxy:edge-socks domain-suffix proxied.example
rule proxy:office-http domain-exact office.example

default direct
```

Rules reference only `proxy:<id>`. Protocol/address data belongs to the endpoint registry.

Configuration rejects:

- invalid endpoint identities
- duplicate endpoint identities
- undefined `proxy:<id>` policy references
- more than 64 named proxy endpoints
- non-IP upstream endpoint addresses in this initial slice

The last restriction intentionally defers proxy-bootstrap DNS semantics until they have an explicit architecture.

### Capability-gated execution

The first proxy endpoints advertise TCP capability only.

If policy selects a proxy endpoint for UDP while that endpoint does not advertise UDP capability, Commeatus does **not** silently fall back to `DIRECT`. The flow stays unsupported until an actual proxy-UDP executor exists.

### Strong end-to-end verification

The new E2E suite includes:

```text
SOCKS5 inbound
   ↓
Policy → Proxy(edge-socks)
   ↓
Native upstream SOCKS5 CONNECT
   ↓
mock upstream proxy
   ↓
TCP echo server
```

and:

```text
HTTP CONNECT inbound
   ↓
Policy → Proxy(edge-http)
   ↓
Native upstream HTTP CONNECT
   ↓
mock upstream proxy
   ↓
TCP echo server
```

Both tests use `opaque-target.invalid`. The local DNS engine has no override for that name. The mock upstream proxy observes the original domain and independently connects the test echo server, proving that proxy-routed domain targets are not accidentally resolved by the local DIRECT DNS path.

## Security / architecture notes

- `Reject` remains an action, not an endpoint.
- The core sees endpoint identity only.
- Upstream SOCKS5/HTTP errors remain local connection failures.
- Proxy destination domains are preserved to the selected proxy endpoint.
- Unsupported proxy UDP does not violate policy by falling back to direct traffic.
- Upstream proxy addresses are currently literal IP socket addresses to avoid hidden bootstrap-DNS behavior.

## Not in this release

- proxy outbound authentication
- TLS transport provider
- Shadowsocks
- Trojan
- VLESS
- Hysteria2 / TUIC
- proxy UDP execution
- endpoint groups / selection strategies
- adaptive endpoint scoring
- live TUN / TPROXY / eBPF interception
- KernelSU/Magisk packaging
- DoH / DoT / DoQ / Fake-IP
- Clash/mihomo/sing-box import or compatible API

The next protocol milestone is intended to add a reusable transport boundary first, then place an encrypted protocol handshake on top of it rather than letting protocol implementations own routing, DNS or transport security configuration.
